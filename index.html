How a paradigm was chosen

Four questions asked of each dataset.

QuestionIf yes, lean toward
Are rows tightly related and must stay consistent?MySQL
Does each record vary in shape and get read whole?MongoDB
Is the question about paths or neighbours?Neo4j
Is it heavy ad-hoc aggregation?MySQL

The dataset

One logical dataset, three physical forms.

  • Generated from a fixed seed, so every run sees identical data.
  • Skewed on purpose: a few popular products and heavy buyers, like real shops.
  • Several sizes from 1M to 100M rows to test scalability.
  • Same facts everywhere: orders as tables, products as documents, follows and purchases as edges.

Benchmark protocol

Rules applied to every measurement.

  • Discard the first runs (warm-up), then repeat each query many times.
  • Report median, p95 and p99, never the average alone.
  • Measure cold-cache and warm-cache separately.
  • Change one variable at a time: index, size or isolation level.
  • Declare indexes before timing and confirm the plan with EXPLAIN, .explain() or PROFILE.
  • Use the same machine, same client and same dataset for all three.

Limits of the comparison

What the numbers can and cannot say.

  • Synthetic data and a single node: results show relative strengths, not absolute speeds.
  • Engines differ in caching, drivers and durability defaults, so each was tuned to comparable settings.
  • Each store was used for what it is built for; a workload one of them is poor at is a finding, not a bug.
  • Results should be re-run on new hardware before being relied on.

Query optimization, step by step


Normalise first, then let the optimizer work: B+-tree indexes, accurate cardinality estimates, a good join order, and materialized views for repeated reports.




Normalization walkthrough
One wide table, split by its functional dependencies.
-- Before: orders_wide (1NF)
(order_id, cust_id, cust_city, prod_id, prod_name, qty)
-- FDs
order_id → cust_id
cust_id  → cust_city        -- transitive: breaks 3NF
prod_id  → prod_name        -- partial: breaks 2NF
(order_id, prod_id) → qty
-- After: BCNF, every determinant is a key
customers(cust_id, cust_city)
products(prod_id, prod_name)
orders(order_id, cust_id)
order_items(order_id, prod_id, qty)

Neo4j: relationships first


Friends-of-friends and "customers who bought this also bought" are path queries. Graphs answer them without join explosions.




Cypher
Recommendations within 3 hops.
MATCH (me:Customer {id:$id})-[:FOLLOWS*1..3]->(f)
      -[:BOUGHT]->(p:Product)
WHERE NOT (me)-[:BOUGHT]->(p)
RETURN p.name, count(*) AS score
ORDER BY score DESC LIMIT 10

Deadlock: two transactions, opposite lock order
InnoDB detects the cycle and rolls back the cheaper transaction.











Two-phase locking
Grow, then shrink. Never lock after the first unlock; that guarantees conflict-serializable schedules.
T1: lock-X(A) read(A) write(A) lock-X(B)
    read(B) write(B) COMMIT  unlock(A,B)
        └ growing phase ┘     └ shrinking ┘
-- strict 2PL holds X-locks until commit
-- avoids cascading rollbacks


MVCC read view
Readers see a snapshot and never block writers.
-- Session 1 (REPEATABLE READ)
START TRANSACTION; SELECT bal FROM acct WHERE id=1; -- 500
-- Session 2 commits UPDATE bal=400
SELECT bal FROM acct WHERE id=1; -- still 500
COMMIT;                       -- next read: 400

What the project showed




Choose MySQL when
Correctness matters most: money, inventory, multi-row invariants, ad-hoc analytics over normalised data.


Choose MongoDB when
Records vary in shape and are read whole: catalogues, content, events. Scale-out comes built in.


Choose Neo4j when
The question is about relationships: paths, recommendations, influence. Cost follows hops, not table size.




The common thread: index for the access pattern you actually have, measure with EXPLAIN or .explain(), and keep one system of record.
